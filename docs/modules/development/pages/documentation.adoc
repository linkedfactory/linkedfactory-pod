= Documentation guidelines
:description: Where documentation goes, which Diátaxis type a page has, and the conventions for writing and building it.

The Pod documentation is an https://antora.org[Antora] component written in AsciiDoc in `docs/`.
It is organised by audience and by https://diataxis.fr[Diátaxis] type.
These guidelines apply to every change to the documentation, by people and by coding agents.

== Audiences and entry points

[cols="1,1,3",options="header"]
|===
|Audience |Entry point |Content

|Users: integrators, modellers, operators
|`README.md`, then `docs/modules/ROOT`
|Running Pod, writing and querying data, configuration, interfaces, concepts.

|Contributors
|`CONTRIBUTING.md`, then `docs/modules/development`
|Building, testing, code structure, documentation, releases.
|===

`README.md` stays short: what Pod is, how to start it, and where to read on.
`CONTRIBUTING.md` covers what a contributor needs before the first pull request and links into the development module.
Neither file repeats content from `docs/`.

== Diátaxis types

Every page has exactly one type.

[cols="1,2,2,1",options="header"]
|===
|Type |Purpose |Reader's question |Module

|Tutorial
|Teach a beginner by doing, with a guaranteed result.
|"Can you show me how this works?"
|`tutorials` (not yet in use)

|How-to guide
|Help a competent user complete one specific task.
|"How do I …?"
|`how-to`

|Reference
|Describe the machinery: interfaces, formats, options, defaults.
|"What exactly is …?"
|`reference`

|Explanation
|Build understanding: context, reasons, trade-offs, relationships.
|"Why …?"
|`explanation`
|===

`ROOT` holds the landing page and the quickstart.
`development` holds contributor pages; each of them also has one Diátaxis type, mostly how-to or reference.

== Rules per type

=== Tutorial

* Leads through one concrete example from start to finish; every step works as written.
* No alternatives, no options, no explanations beyond one sentence; link to them instead.
* Ends with what the reader has achieved and where to continue.

=== How-to guide

* The title states the goal, for example "Enable full-text search", not "Full-text search".
* Starts with a short statement of the goal and the prerequisites that are really required.
* Steps are ordered, imperative, and have action-oriented headings.
* Shows how to verify the result.
* Links to reference and explanation instead of embedding them.

=== Reference

* Structured like the thing it describes: one section per endpoint, property group, or command.
* Neutral and complete: names, types, defaults, limits, errors.
* Tables for lists of parameters or properties; short examples where they help.
* No instructions and no rationale; link to the matching how-to or explanation.

=== Explanation

* Answers "why" and "how does this relate": design decisions, trade-offs, consequences.
* May discuss alternatives and history.
* Contains no step-by-step instructions and no exhaustive option lists.

== Choosing the type

If content does not fit the type of the page you are editing, put it on a page of the matching type and link to it.

* A page that mixes steps with long background sections is split into a how-to and an explanation.
* A how-to that lists every option is split into a how-to (the common path) and a reference (all options).
* New content that answers "why" goes to `explanation`, even if it was found while writing a how-to.

== Conventions

* Write in English.
* Every page starts with a title and a `:description:` attribute.
* Cross-references always name the module: `xref:how-to:query-data.adoc[]`.
* Shared snippets go to `ROOT/partials`, images to `ROOT/images`.
* Add every new page to the `nav.adoc` of its module. Pages that describe eniLINK functionality are grouped under "Platform (eniLINK)".
* Check statements against the code and configuration in the repository, not only against other documentation.
* Do not add placeholder pages or outlines. A page is added when its content is written.
* Use admonitions (`NOTE`, `IMPORTANT`, `WARNING`) only for information whose omission causes harm, such as default credentials or data loss.
* Update the documentation in the same pull request as the code change it describes.

== Build the documentation locally

`antora-playbook.yml` in the repository root builds the site from the local working tree:

[source,bash]
----
npx antora@3.1 --fetch antora-playbook.yml
----

The output is written to `build/site`.
The build fails on broken cross-references and includes.

== Publishing

The workflow `.github/workflows/docs.yml` builds the site with the same playbook.
For pull requests that change `docs/` it only builds, as a check.
For changes on `main` it also publishes the site on GitHub Pages.
