= Writing documentation
:description: Structure, conventions, and local build of the Pod documentation.

The documentation is an https://antora.org[Antora] component written in AsciiDoc.
It lives in `docs/` and is organised by audience and by https://diataxis.fr[Diátaxis] type.

== Where pages go

[cols="1,1,3",options="header"]
|===
|Module |Audience |Content

|`ROOT` |Users |Landing page, installation, quickstart, shared partials and images.
|`tutorials` |Users |Guided lessons with a guaranteed result.
|`how-to` |Users, operators |Instructions for one specific task.
|`reference` |Users, integrators |Exact description of APIs, formats, configuration, CLI.
|`explanation` |Users |Concepts, architecture, design decisions.
|`development` |Contributors |Build, test, internals, extension, release, documentation.
|===

Pages that describe eniLINK functionality are listed under "Platform (eniLINK)" in the navigation of their module.
`README.md` and `CONTRIBUTING.md` stay in Markdown and link into this site.

The plan behind this structure, including open follow-up work, is in `docs/diataxis/plan.md`.

== Conventions

* One page has one Diátaxis type. Move other content to a page of the matching type and link to it.
* Cross-references always name the module: `xref:how-to:query-data.adoc[]`.
* Shared snippets go to `ROOT/partials`, images to `ROOT/images`.
* Keep admonitions for warnings that matter, such as default credentials or data loss.

== Build locally

The playbook `antora-playbook.yml` in the repository root builds the site from the local working tree:

[source,bash]
----
npx antora@3.1 --fetch antora-playbook.yml
----

The output is written to `build/site`.
CI runs the same build for every pull request that changes `docs/` and fails on broken references.
