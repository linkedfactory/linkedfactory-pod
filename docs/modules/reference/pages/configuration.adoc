= Configuration
:description: Configuration files, storage, users and permissions, login, query timeout, bundle settings, and system properties of Pod.

Pod is configured on two levels:

* The *platform configuration* of eniLINK, an RDF file usually named `config.ttl`. It defines storage, users, groups, permissions, login, and the query timeout.
* *Bundle configurations* for Pod's own services, for example the KVIN store.

Changing one does not change the other: selecting an RDF repository does not select a KVIN store.

== Platform configuration file

[cols="1,2",options="header"]
|===
|Setup |File

|Docker image
|`config.ttl` in the workspace volume. On first start, the image copies its default there; later starts keep your version.

|Local launch from `launch/equinox`
|`configurations/default.ttl`, set through `net.enilink.config` in `launch/equinox/pom.xml`.
|===

eniLINK selects the platform configuration in this order:

. The JVM property `net.enilink.config`, if it names a readable path or absolute URI.
. `config.ttl` in the workspace (Eclipse instance location).
. `config.ttl` in the installation directory.

The file can include others with `owl:imports`; relative IRIs resolve against the file's location.
The startup log shows which files were loaded.

Without any configuration, eniLINK starts with full anonymous access.
The JVM property `net.enilink.acl.anonymous=all` has the same effect.
Removing `config.ttl` therefore opens Pod instead of closing it.

== Storage

[cols="1,2",options="header"]
|===
|Setting |Stores

|`urn:enilink:data`
|RDF models with asset descriptions and ontologies, with Pod's KVIN query integration.

|`urn:enilink:metadata`
|Platform metadata such as model owners and permissions, if configured separately.

|JVM property `net.enilink.filestore.path`
|Attached files. Default: `files/` in the workspace.

|Bundle configuration `io.github.linkedfactory.service`
|The KVIN store for measurements and the default model, see <<_bundle_configuration>>.
|===

The shipped configuration uses `models:KvinMemoryModelSet`: RDF models are kept in memory and lost on restart.
For persistent models, use `models:KvinPersistentModelSet`; a generic eniLINK model set would lose the KVIN query integration:

[source,turtle]
----
@prefix models: <http://enilink.net/vocab/komma/models#> .

<urn:enilink:data>
    a models:KvinPersistentModelSet ;
    models:inference false ;
    models:repository <workspace:/data/> .

<urn:enilink:metadata>
    a models:PersistentModelSet ;
    models:inference false ;
    models:repository <workspace:/meta/> .
----

`workspace:/` resolves within the workspace.
After changing the storage, restart Pod and check that models and a query with `SERVICE <kvin:>` still work.
Existing data is not migrated.

To add full-text search, the data model set is defined as a repository with a SAIL chain, see xref:how-to:enable-full-text-search.adoc[].

Back up RDF data, metadata, files, configuration, and the KVIN store together.

== Users, groups, and permissions

Users (`enilink:user:…`, `foaf:Agent` with `auth:password`), groups (`foaf:Group` with `foaf:member`), and authorizations (`acl:Authorization`) are defined in the platform configuration and read at startup.
xref:how-to:grant-access-with-groups.adoc[] shows an example; xref:explanation:security-model.adoc[] explains the model.

== Query timeout

[source,turtle]
----
@prefix config: <enilink:config/> .

config: config:queryTimeout 60000 .
----

The value is in milliseconds.
Without it, eniLINK uses `20000`; the shipped configuration sets `60000`.
It applies to query execution on models, not to HTTP connections or storage.
A query that exceeds it fails with `503 QUERY_TIMEOUT`.

== Login

[source,turtle]
----
@prefix login: <plugin://net.enilink.platform.core/Login/> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

login:
    login:jaasConfigUrl <jaas.conf> ;
    login:loginModule [
        login:jaasConfigName "LinkedFactory-POD" ;
        rdfs:label "LinkedFactory-POD"
    ] .
----

`login:jaasConfigName` must match an entry in the JAAS file; Pod's `configurations/jaas.conf` defines `LinkedFactory-POD` with eniLINK's `EnilinkLoginModule`.
Several login methods can be configured; `rdfs:label` is the name shown in the browser.
Without this configuration, eniLINK uses its own JAAS file and a method named `eniLINK`.

The JVM property `enilink.loginrequired=true` makes the browser interface require a login.
It does not change model permissions or protect the time-series API.

== Bundle configuration

For the bundle `io.github.linkedfactory.service`, eniLINK uses the first file it finds:

. `config/io.github.linkedfactory.service.ttl` in the workspace
. the same file under the installation directory
. `OSGI-INF/io.github.linkedfactory.service-default.ttl` in the bundle

A file replaces the default completely; it is not merged.
Include all settings you need.

Example with the default model and a LevelDB store:

[source,turtle]
----
@base <plugin://io.github.linkedfactory.service/data/> .

<> <defaultModel> <http://linkedfactory.github.io/data/> ;
   <store> [
       a <KvinLevelDb> ;
       <dirName> "linkedfactory-valuestore"
   ] .
----

A LevelDB store records the version of its storage format.
Pod does not open a store that was created by an earlier version without this record, or that has another format version; it fails with an error that names the store directory.
Pod does not convert such stores.
To start with an empty store, set a new `dirName` or remove the old directory.

=== Partitioned storage

A partitioned store writes new values to LevelDB and moves them to an Iceberg archive at a fixed interval:

[source,turtle]
----
<store> [
    a <KvinPartitioned> ;
    <dirName> "linkedfactory-partitioned" ;
    <archiveInterval> "P7D" ;
    <retentionPeriod> "P30D"
] .
----

[cols="1,3",options="header"]
|===
|Setting |Meaning

|`dirName`
|Store directory. Default: `linkedfactory-partition`.

|`archiveInterval`
|Time between two archival runs. The first run starts when Pod starts. Without this setting, values stay in LevelDB.

|`retentionPeriod`
|Optional. After each archival run, archived values that are older than this period are removed.
|===

Both durations are ISO 8601 durations such as `P7D`, or a number of milliseconds.
New values go to `current/`; the archive in `archive/` is an Iceberg store as described in <<Iceberg storage>>.
Queries read both.
Deletes only change values that are not archived yet.

Pod does not open a store whose `archive/` directory holds a Parquet archive of an earlier Pod version; it fails with an error that names the directory.
Pod does not convert such archives.
To start with an empty archive, set a new `dirName` or remove the old directory.

=== Iceberg storage

To use Iceberg instead of the default value store, configure a store of type `KvinIceberg`:

[source,turtle]
----
<store> [
    a <KvinIceberg> ;
    <dirName> "linkedfactory-iceberg" ;
    <retentionPeriod> "P365D" ;
    <tableProperties> """
        kvin.compaction.min-files=8
        write.target-file-size-bytes=268435456
    """
] .
----

[cols="1,3",options="header"]
|===
|Setting |Meaning

|`dirName`
|Archive location. Default: `linkedfactory-iceberg`. A path is relative to the workspace. A URI such as `s3a://bucket/pod-archive` is used unchanged, see the remote locations below.

|`retentionPeriod`
|Optional. Each cleanup removes the values that are older than this period.

|`cleanUpInterval`
|Optional. Time between two cleanups. The first cleanup runs one interval after Pod starts. Default: `P1D` if `retentionPeriod` is set, otherwise no cleanups.

|`partitionSpec`
|Optional. Partitioning of the value table as Iceberg partition-spec JSON, see below.

|`tableProperties`
|Optional. Iceberg table properties of the value table, one `key=value` per line, see the table of properties below.

|`hadoopProperties`
|Optional. Hadoop properties for accessing the archive, one `key=value` per line, for example `fs.s3a.endpoint=https://s3.example.org`.
|===

Both durations are ISO 8601 durations such as `P7D`, or a number of milliseconds; an invalid duration fails initialization.
A cleanup removes old values and expires old snapshots, as described for `cleanUp()` below.
The table properties are set when the value table is created.
When Pod opens an existing table, it commits the configured properties whose values differ.
Properties that you remove from the configuration keep their values in the table.
Invalid values of the `kvin.` properties and of the size properties below fail initialization.
The Hadoop properties apply to the value table and the URI-ID tables.
Do not put credentials in the configuration file; Hadoop's S3A connector also reads them from environment variables and `~/.aws/credentials`.

KvinIceberg maintains a value table in `iceberg/` and separate URI-ID tables in `iceberg-ids/items/`, `iceberg-ids/properties/`, and `iceberg-ids/contexts/`, with bounded in-memory lookup caches.
Its Parquet V2 data files have separate typed value columns (enabling encodings such as delta packing) and use ZSTD compression; reads follow Iceberg snapshots and use a value-skipping Parquet reader.
KvinIceberg does not open a directory that holds a Parquet archive of an earlier Pod version.

The standalone `IcebergRecordStore` implements `KvinRecordStore` and operates exclusively on numeric `KvinRecord` identifiers, without creating or reading URI-ID tables.
Null contexts select ID `0`; null properties and the interface's `-1` property sentinel select all properties.
Latest-value fetches include negative timestamps.
`IcebergIdStore` implements `IdStore` for all `IdKind` values and can be used without a record store.
Location-based constructors take the archive root and preserve the existing directory layout.
`KvinIceberg`, `IcebergRecordStore`, and `IcebergIdStore` also take a `KvinIcebergOptions` object with all settings of the service configuration; the URI-ID store uses only its location and Hadoop properties.
The root is a local path, a `file:` URI, or a URI of another Hadoop file system, such as `s3a://bucket/archive`.
Pod does not include connectors for remote file systems; the connector for the scheme must be on the classpath.
In the service configuration, set `dirName` to the URI.
Hadoop shares one file system instance per scheme and bucket within the JVM, so the first store that accesses a bucket determines its Hadoop settings.
The property `fs.<scheme>.impl.disable.cache=true` gives each store its own instance.
Fetches read local data files directly, without the Hadoop file system and without vectored I/O.
They read remote data files through the Hadoop file system with vectored I/O, which requests the pages of a row group in parallel.

[source,java]
----
try (var records = new IcebergRecordStore("archive");
     var ids = new IcebergIdStore("archive")) {
    var kvin = new KvinIceberg(records, ids);
    // Use kvin with URIs, or records and ids independently.
}
----

The injected stores remain caller-owned; closing the facade does not close them.
The existing location-based `KvinIceberg` constructors own and close both stores.
`createBranch` delegates to an injected `IcebergRecordStore` (other record-store implementations need not support branches).
A location-based facade refuses to open populated record tables with missing ID tables rather than inventing replacement mappings.

New value tables are unpartitioned by default.
Both `IcebergRecordStore` and `KvinIceberg` accept a third constructor argument, a `Function<Schema, PartitionSpec>`:

[source,java]
----
try (var kvin = new KvinIceberg("archive", null, schema ->
        PartitionSpec.builderFor(schema)
            .bucket("itemId", 32)
            .identity("contextId")
            .truncate("time", 86_400_000)
            .build())) {
    // Write and query normally; Iceberg prunes partitions using existing filters.
}
----

Partition sources may be `itemId`, `contextId`, `propertyId`, `time`, or `seqNr`.
Avoid identity partitioning high-cardinality IDs.
`time` is a long, not an Iceberg timestamp: for epoch-millisecond data, `truncate("time", 86_400_000)` creates fixed-width day-sized ranges (including correctly floored negative timestamps), not calendar-aware timestamp transforms.
Each output file contains only one partition and retains the KVIN sort order and series-start markers.
ID tables remain unchanged.

Omitting the partition factory (or passing null) adopts a reopened table's persisted spec.
Supplying a factory verifies compatibility and rejects mismatches rather than silently evolving the table.
Partition evolution is an explicit Iceberg metadata operation; reads support historical specs, new writes use the current spec, and delete rewrites repartition retained rows using the current spec.

Both `IcebergRecordStore` and `KvinIceberg` accept a retention period as the second constructor argument.
It must be positive.
`cleanUp()` then removes all values that are older than the retention period, in one commit.
With a cleanup interval in `KvinIcebergOptions`, a `KvinIceberg` that opened the archive itself runs `cleanUp()` in a background thread at that interval; closing it waits for a running cleanup.
Data files that contain only older values are dropped without being rewritten; other files that contain them are rewritten without them.
With a partition on `time`, most old files are dropped as a whole.
`deleteOlderThan(time)` of `IcebergRecordStore` removes the values before a given time in the same way.

`cleanUp()` also expires old snapshots of the value table, with or without a retention period.
A snapshot expires once a newer snapshot has replaced it for longer than the table property `history.expire.max-snapshot-age-ms` (default 5 days).
Data files that no remaining snapshot references are then deleted from disk.
Snapshots of branches, and as many snapshots as the table property `history.expire.min-snapshots-to-keep` requires, are kept.
`expireSnapshots()` of `IcebergRecordStore` expires snapshots without removing values.
The URI-ID tables keep all their snapshots.

`delete(context)` removes all values of a context in one commit.
Data files that contain only this context are dropped without being rewritten; other files that contain it are rewritten without its rows.
With an `identity("contextId")` partition, every file holds a single context, so deleting a context does not rewrite any data.

For service configuration, optional `<partitionSpec>` accepts native Iceberg partition-spec JSON.
For example, item bucketing with 32 buckets:

[source,turtle]
----
<store> [
    a <KvinIceberg> ;
    <dirName> "linkedfactory-iceberg" ;
    <partitionSpec> """{"spec-id":0,"fields":[{"name":"item_bucket","transform":"bucket[32]","source-id":1,"field-id":1000}]}"""
] .
----

Source field IDs are 1 (`itemId`), 2 (`contextId`), 3 (`propertyId`), 4 (`time`), and 5 (`seqNr`).
Use `PartitionSpecParser.toJson(spec)` to generate configuration from a Java-built spec.
`KvinIcebergOptions.builder(location).partitionSpec(json)` also accepts this JSON without exposing Iceberg types to callers in other OSGi bundles.
Omit `<partitionSpec>` to use the default/adoption behavior; invalid JSON, unsupported sources, and incompatible specs fail initialization.

The following Iceberg table properties of the value table control how data is written.
Set them with `<tableProperties>` in the service configuration, with `KvinIcebergOptions.Builder.tableProperties`, or with Iceberg's `Table.updateProperties()`; each write reads the current values.

[cols="2,1,3"]
|===
|Property |Default |Meaning

|`kvin.write.batch-records`
|131072
|Number of records that a write sorts in memory and stores as one data file per partition. A write with more records creates several files. Must be at least 1.

|`write.parquet.row-group-size-bytes`
|8 MB
|Parquet row group size of data files. Compaction limits it to the target file size.

|`write.parquet.page-size-bytes`
|8 KB
|Parquet page size of data files. Reads skip pages that cannot contain the requested values.

|`kvin.compaction.min-files`
|8
|Number of files of one tier in a partition that are merged together. Also the factor between tiers. Must be at least 2.

|`write.target-file-size-bytes`
|128 MB
|Target size of compacted files. Files smaller than half of it are compacted.
|===

ID allocation stages mappings, including forward and reverse lookups, until `flush()` or `close()`; batches automatically flush at 8192 new mappings.
In a local archive, allocation is serialized using `iceberg-ids.lock`, held until flushing, so independent processes must flush before waiting for another process to allocate.
A remote archive has no lock file, so only one process may write to it.
Instances within the same JVM coordinate automatically, flushing the previous writer when another instance allocates.
The facade resolves IDs in batches and flushes mappings before passing records to the record store, keeping pending mappings and record buffers bounded.
A flush failure retains the allocation lock and pending mappings for retry, preventing reassignment of IDs already handed to callers.

`IdStore.getIds(uris, kind, createIfNotExists)` and `getUris(ids, kind)` return maps keyed by distinct inputs, without a result-order guarantee.
Unknown URIs are omitted when creation is disabled; unknown reverse IDs raise an error.
Default implementations support single-lookup stores, while `IcebergIdStore` resolves cache misses with one filtered scan per batch.
Fetches without explicit properties buffer up to 1024 records (or the requested per-series limit, if smaller) to batch reverse property lookups, preserving record order and reusing mappings throughout the query.
Explicit-property fetches do not read ahead.

The value table declares the sort order `contextId ASC, itemId ASC, propertyId ASC, time DESC, seqNr DESC` in Iceberg metadata.
Each batch is physically sorted in that order, and new data files record its sort-order ID.
Opening an existing store updates the table's default sort order if needed, without rewriting or relabeling old files.
Sorted data and column statistics support scan pruning; sort-order metadata alone does not guarantee faster searches or globally ordered query results.

After each successful append, the store starts a tiered compaction in a background thread.
Only one compaction runs at a time per store; writes and reads do not wait for it.
A value file's tier is `floor(log~F~(record count))`, where F is the Iceberg table property `kvin.compaction.min-files` (default 8, minimum 2).
When a partition and spec ID has F files of one tier, compaction merge-sorts them into files of a higher tier, starting with the lowest such tier, and repeats until no tier has F files.
Each value is therefore rewritten at most once per tier.
Files smaller than half `write.target-file-size-bytes` are eligible; output files roll at that target (128 MiB if unset).
Each merge takes at most 128 files, or F if larger, without merging different partitions or relabeling historical specs.
Compaction preserves duplicates, series-start markers, and files referenced by existing readers and snapshots.
Background compaction failures are logged; the appended data remains committed, and the next append starts another compaction.
`IcebergRecordStore.compact()` runs a compaction in the compaction thread, waits for it, and throws its failures.
A compaction that conflicts with a concurrent delete fails and removes its output files; an uncertain compaction commit retains its output files rather than risking data loss.
Closing the store waits for a running compaction and skips queued ones.

Every output file regenerates `first=true` for the first row of each item/context/property series, including a series continued from the preceding output file, so property discovery remains correct after compaction.

Manifest caching is enabled for both new and reopened value and URI-ID tables.
It uses Iceberg's defaults: up to 100 MiB per table FileIO, with individual manifests limited to 8 MiB and entries expiring after 60 seconds without access.
Caches are released when the store closes.
Tables still refresh for every query, so caching immutable manifests does not delay visibility of committed writes from other instances; Parquet data is not cached.

Fetches batch uncached item and property URI lookups, merge sorted files with constant-size per-series limit bookkeeping, and defer advancing a reader until another tuple is needed.
Data files are opened lazily: planned files are ordered by the smallest matching key their column statistics allow (item, property, and latest time), and a file is opened only when that bound is not after the current merge head.
A latest-value query on time-ordered data therefore usually opens a single file.
Parquet footers are cached per data file (up to 4096 files); entries for files replaced by compaction or deletes are dropped.
Limited reads skip value decoding for completed series and use the advancing series boundary to prune subsequent Parquet row groups.
Non-aggregated queries with explicit properties close their readers as soon as every requested item/property combination has reached its limit.
Queries without explicit properties, or with combinations that have fewer matching tuples than the limit, continue looking for remaining series.
Property listing projects only identifiers and per-file series-start markers, then resolves distinct property IDs in a batch; it does not read or decode value columns.
Built-in aggregations accumulate values without buffering an entire time interval; their limits apply to aggregated results, not input tuples.

eniLINK watches bundle configuration files.
When one changes, the affected bundles are stopped and restarted, which interrupts their service.
Prepare changes completely and apply storage changes in a maintenance window.
The platform configuration is not reloaded this way; restart Pod after changing it.

== Models loaded at startup

The OSGi property `net.enilink.models.dir` names a directory whose `.ttl` and `.owl` files become models at startup.
A file that declares an ontology IRI is registered under that IRI, so other models can import it by IRI, see xref:explanation:semantic-concepts.adoc[].

== Remote repositories

For repository types that connect to a server, the JVM properties `net.enilink.data.server`, `net.enilink.data.username`, and `net.enilink.data.password` override the corresponding settings of the data model set; `net.enilink.metadata.…` does the same for the metadata.
They do not select a repository type or configure the KVIN store.
Keep the password out of version control.

== Setting system properties

JVM system properties are not environment variables.

* Docker image: pass them through the Karaf start script, for example `-e EXTRA_JAVA_OPTS="-Denilink.loginrequired=true"`.
* Local launch: add them to the `vmProperties` in `launch/equinox/pom.xml`.

The setting `enilink.loginrequired=false` in `docker/docker-compose.yml` is an environment variable and has no effect; the login is not required by default anyway.
